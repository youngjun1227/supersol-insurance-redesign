## 0. 먼저 읽을 것 — 이 문서의 상태

1. **여기 적힌 것은 전부 검증 전 가설이다.** 설문은 8/15~8/19 진행 중이고, 가설 확정과 Gate 1(P 카드 확정)은 **8/25 종합 회의**에서 한다. 그 전까지 그리는 모든 화면은 **"가설 기반 시안"**이다. "개선안"·"솔루션"이라는 이름은 8/25 이후, P 카드에 연결된 것에만 붙인다 (Research Rule 10).
2. **8/25에 P로 확정되지 않은 가설의 화면은 시안에서 뺀다. 이미 그렸어도 뺀다.** "이미 그렸으니 넣자"가 이 프로젝트에서 가장 위험한 문장이다. 그래서 **화면마다 어느 H에 기대고 있는지 태그를 붙여 두어야** 8/25에 빼고 넣기가 쉽다.
3. **목표는 "SuperSOL 보험 탭을 더 예쁘게"가 아니다.** 근거 카드가 가리키는 문제 후보를 풀어서, 9/11 사용자 테스트에서 **기존 앱 vs 우리 MVP**로 비교 측정할 수 있는 화면을 만드는 것이다. 룩앤필은 SuperSOL과 크게 다르지 않아야 비교가 공정하다.
4. 표현 규칙: "사용자는 ~를 불편해한다", "명백히", "확실히"를 쓰지 않는다. "~할 가능성이 있다", "가설: ~"로 쓴다.
5. **AI는 안을 여러 개 내는 역할이다. 고르는 것은 팀이다.** 한 문제에 2~3안을 만들고, 팀이 고른 결과와 이유는 `_meta/decision_log.md`에 회의 때 적는다.

## 1. 프로젝트 한 줄
**신한 SuperSOL(슈퍼쏠) 앱의 보험 화면 UX 개선.** 주 대상은 20대. 산출물은 React 모바일웹 MVP(목데이터, 백엔드 없음, 화면 4~6개)이며 9/11부터 사용자 테스트, 9/20 발표.

**일정** — 와이어프레임 8/15~19 → 최종 UI 디자인 8/20~24(팀원2 주도) → 🔒 8/25 종합 회의(H 확정 + Gate 1 + 시안 대조) → React MVP 8/25~31(팀장) → 9/1~ 다듬기·배포 → 🔒 9/11 사용자 테스트.

**현재 SuperSOL 보험 화면 구조 (팀 관찰 O 카드 기준)**
- 보험 입구 3곳: ① 금융 탭 > 보험(조회·청구·"보험 추천 서비스" 12개) ② 상품 탭 > 보험(상품 목록) ③ 사이드메뉴 > 보험 — 이름은 셋 다 "보험"
- 상품 목록은 **[신한은행] / [신한라이프] 전환 탭**. 신한은행 = 타사 상품만, 신한라이프 = 자사만. 카테고리 이름 4개(암·건강·치아·상해)가 겹치는데 상품은 안 겹침. 왜 나뉘는지 설명 없음
- "보험 추천 서비스" 12개가 같은 크기·형태. 보험금청구는 스크롤해야 보임. 정보(건강사전·AI영양분석)와 거래(신청·납입)가 같은 자리
- "보장에너지": "보장금액이 하나도 없어요" + 전문가 상담 연결. 수치·비교 기준 없음
- 홈은 AI 개인화 표방하지만 보험 화면은 누구에게나 같음

> ⚠️ SuperSOL 캡처 S 카드는 리서치 저장소에 아직 없음. **이 디자인 저장소에는 캡처 16장(`00_reference/screenshots/`)과 AS-IS 와이어프레임 8장이 있음** — S 카드 작성 시 이걸 쓰면 됨.

## 2. 개선 아이디어 — 가설별 (근거 두께 순)

### A. 상품 목록을 회사 축이 아니라 보장 카테고리 축으로 — `H-002` ★근거 가장 두꺼움
- 가설: "누가 파는가"로 먼저 나뉘고 기준 설명이 없어, 보장으로 찾는 사용자가 한쪽 탭만 보고 나갈 가능성
- 사실: O-102·103·104·202·303·304·406 (관찰 8장). 경쟁: 모니모 C-304(금융상품 종류 축), 토스 C-404(상황 문장 축, 회사명은 카드 제목)
- 시안 방향: 공통 카테고리(보장/저축투자) 상단, [신한은행/신한라이프]는 아래(필터 or 판매사 뱃지). 구분 기준 한 줄 설명
  → **2~3안**: ① 카테고리 탭 상단 + 회사 필터 칩 ② 카테고리 상단 + 카드마다 판매사 뱃지(탭 없음) ③ 토스식 상황 문장 카테고리
- 설문: Q5·Q6 → 8/25 판정
- 주의: 효과는 사용자 관점("찾는 상품에 더 빨리 닿는다")만. "신한라이프 노출 증대" 금지(E-102 25% 룰). 카테고리 통일 가능 여부 멘토 확인

### B. 청구 입구를 앞으로, 서비스 12개에 위계·묶음 — `H-003` + `H-006`
- 가설: 청구가 "추천 서비스" 하위에 있어 못 찾을 가능성 / 12개가 위계·묶음 없이 거래·청구·정보 섞여 판단 부담
- 사실: O-106·203·401·402·403·205. 경쟁: 모니모 C-301·305(현황 카드 + "가입|청구" 2분할, 청구 2탭·무스크롤, 절차 4단계 안내), 토스 C-404("하는 일" 4개 한 섹션)
- 시안 방향: 메인 상단 핵심 행동 2~3개(내 보험 / 청구 / 찾기), 나머지는 성격별 묶음(조회·계약 / 청구·신청 / 정보·콘텐츠). 청구는 무스크롤
  → **2안**: ① 모니모식 현황 카드 + 2분할 버튼 ② 토스식 "하는 일" 섹션 + 탐색 섹션
- 검증: 9/11 테스트 과제("청구 화면까지 가기", "계약조회 찾기") 시간·시도·성공률
- 주의: 12개 중 뭐가 자주 쓰이는지 데이터 없음 → 묶음 기준은 "성격"으로만. 개수 자체가 문제라는 근거 없음

### C. 보장에너지에 수치·비교 기준·설명 — `H-004` (가) 정보 제공 해석
- 가설: "하나도 없어요"+상담 연결뿐이라 판단 근거로 못 쓰고 가입 권유로 읽혀 이탈 가능성
- 사실: O-404·405(보유 0건 계정). 경쟁: 토스 C-402(또래 비교 금액, 부족 항목 뱃지, 오각형, 비교 기준 문장, 한계 문구, "강요 안 함"), 모니모 C-302(부족 11개·또래 평균·별명)
- 시안 방향: 항목별 수치 / 비교 기준 문장 / 한계 문구 / 상담·가입은 정보 뒤 → **2안**: ① 수치 목록형 ② 그래프+뱃지형
- 설문: Q9 (④부담스럽다 다수면 약해짐)
- 주의: "자사 상품 가입 연결"은 근거와 반대. (가) 정보 제공으로만 그림

### D. 보험 입구 3곳 이름·도착지 예측 가능하게 — `H-001`
- 가설: 셋 다 "보험"인데 도착 화면 달라 못 고르고 상호 이동 안내 없음
- 사실: O-301·302·101. 경쟁: 모니모 C-306·301(목적별 라벨), 토스 C-406(입구 1개+검색)
- 시안 방향: 라벨에 목적 / 상호 이동 링크 / 입구 통합+탭 분기. **MVP는 보험 메인 1장에서 "조회/찾기/청구" 분기로 흡수(B와 같은 화면)**
- 주의: "클릭 3회 깊다" 주장 안 함. 문제 후보는 분기의 불명확성

### E. 사용자 상태에 맞는 구성 — `H-007`
- 가설: 누구에게나 같은 구성이라 판단이 사용자에게 넘어감
- 사실: O-105·201. 경쟁: 토스 C-406·401(계정 상태별 메인 분기), 모니모 C-306(반고정 홈 편집)
- 시안 방향: MVP는 "보유 0건 20대" 1개 상태만 → **2안**: ① 상단 맞춤 카드 1장 + 공통 ② 토스식 전체 분기
- 설문: Q7·Q12 (Q12 ③ 다수면 빠짐)
- 주의: 데이터 우려(E-133·135·126) → "왜 보이는지" 한 줄 + 끄기/기준 바꾸기. 8/25 전 후순위

### F. 정보 콘텐츠를 필요한 자리에 — `H-005`
- 가설: 용어가 막히는 순간에 닿는 구조가 아닐 가능성
- 사실: O-403 하나. SuperSOL 상세의 용어 설명 장치 유무 미관찰 → 상세 시안 보류
- 경쟁: 모니모 C-303(풀이 잘돼 있으나 4단계 깊이), 토스 C-403(없음). 세 앱 모두 못 푸는 지점
- 시안 방향: 목록/상세 용어 옆 인라인 툴팁·한 줄 풀이. 목록 툴팁 1~2개로 최소
- 설문: Q3·Q4

### G. 병원 결제 감지 → 청구 알림 — `H-008` ⚠️ 근거 약함·후순위
- 사실: 팀 관찰 0장. E-119(미청구 90.6% "소액") 반대 자료. 토스가 이미 운영 중
- 시안 방향: 그린다면 앱 진입 팝업 → 청구 화면 1~2장. 알림 자체(카톡)는 MVP 밖
- 설문: Q8. 주의: 규제(E-137) 실현 가능성 멘토 확인. **가장 나중, 8/25 후**
